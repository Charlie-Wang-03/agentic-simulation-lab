## Solver-derived publication surface

The machine-readable inventory at `docs/release/SOLVER_DERIVED_PUBLICATION_INVENTORY.json` closes the tracked publication surface at one upstream review unit per domain solver-run corpus. This is intentionally broader than the 11 final simulation figures. It covers reference JSON, copied result/status values in manifests and reports, release-regression summaries, generated README/gallery/showcase content, and the 11 sanitized evidence/PNG/SVG sets. Derived files inherit the status of the corpus that supplied their solver-derived information; they do not each require a duplicate legal record.

Each review unit's `source_fingerprint` binds its status to the exact sorted set of matched relative paths and SHA-256 hashes of canonical UTF-8/LF JSON content. Canonical line endings make the same reviewed Git content portable across Windows worktrees and clean archives. Adding, removing, renaming, or changing a reference still makes the fingerprint stale and fails the audit until the corpus is reviewed again and the inventory is deliberately updated. A wildcard selects the candidate corpus; it never extends an earlier clearance or decision to new content.

The tracked references include product/version hints, and some multiphysics records identify use of project-local official assets. Project-local run records also provide sanitized timestamps and solver outcomes. None of those facts establishes the actual License Type, applicable Agreement, complete run purpose, or publication/redistribution basis for every constituent historical run. Each domain corpus therefore remains `LEGAL_REVIEW_REQUIRED`; no legal conclusion about the historical runs is made. A corpus must be split before clearance if its constituent runs have materially different licensing or input facts.

Analytical equations, analytical/reference values, public factual identifiers, and prose not copied from solver output remain outside this gate. A mixed JSON or Markdown file is gated only through the solver-derived information it contains; the presence of an analytical comparison value does not itself trigger review.

Future evidence proposed for public release must identify its source review unit and record generation date, solver/product, actual License Type if known, applicable Agreement, run purpose, source/input provenance, proprietary/vendor-asset involvement, and publication basis truthfully at that unit. Use `unknown` rather than inference. Only a record supported by the applicable terms may use `CLEARED`. Future Ansys runs primarily for academic research, paper experiments, research datasets, or authoritative paper figures/results are a new licensing context and do not inherit the historical decision.

## Publication rule

Technical source classification, legal/evidence status, and maintainer publication decision are independent layers. `BLOCKED` cannot be approved. `LEGAL_REVIEW_REQUIRED` may pass the publication gate only with an explicit `APPROVED_WITH_RESIDUAL_RISK` decision and a visible warning; it never becomes `CLEARED`. The current decision and its bounded rationale are recorded in `MAINTAINER_PUBLICATION_DECISIONS.json`.

Apache-2.0 applies only to rights held by project contributors. Solver-derived numerical evidence and project-rendered figures are published as project validation evidence; the repository grants no underlying rights in Ansys software, documentation, trademarks, official/vendor assets, or other third-party materials.
